### 源码与报告字段的对应

核心实现为 [`autobuild.py`](../services/draft/draft/autobuild.py) 的 `auto_build()`。以下行号以已验证代码提交 `1a2bc468...` 为准，用于从报告字段回查实际控制流程。

|报告字段 / 行为|源码位置|实现与判定|
|---|---|---|
|`attempts[].build_exit_code`、`failure_class`|第 105–111 行|保存每轮 Docker 构建退出码；首轮日志经 `classify_failure()` 分类。只有实际构建失败且类别为 `MISSING_MAKE` 才进入候选轮次，网络等环境故障不能冒充目标错误。|
|`attempts[1].image_id`|第 115–120 行|候选构建成功后执行 `docker image inspect`。先检查命令退出码，非零即抛出 `Cannot inspect built image`；仅成功时解析 inspect JSON 并保存镜像 ID。|
|`verification`|第 121–128 行|把同一个 `image_id` 作为 `docker run` 的最后一个参数，禁网并限制 CPU、内存和进程数；保存命令、退出码及 stdout。`output_matches` 按去除末尾换行后的输出比较；程序退出码非零或输出不匹配都会使流程失败。|
|`status` 与结果落盘|第 129–144 行|构建与验证均成功才设为 `SUCCEEDED`；超时设为 `TIMED_OUT`，其他已处理异常设为 `FAILED`。`finally` 根据保存的容器 ID 尝试清理，并将报告写入 `result.json`。|

新增测试 [`test_image_inspect_failure_stops_before_verification`](../services/draft/tests/test_workflow_failures.py) 对应第二、三行：模拟 inspect 退出非零但 stdout 仍是可解析的镜像 JSON，要求结果为 `FAILED`，不保存有效 `image_id` 或 `verification`，也不执行任何 `docker run`。它验证“命令成功”是接受镜像 ID 的前提，不能只因 stdout 看起来正常就继续运行。
